## Outline

Because the Kakoune plugin offers user modes (select, transform, inside and around, voicing) that the VS Code extension lacks, we bring them to the extension as a modal menu, a list view and a keyboard panel. Testing is part of each phase.

1. Phase 1: keymap data, loader and resolver. These are pure modules without any `vscode` import.
2. Phase 2: the voicing commands accept a voice count, and the new settings are declared.
3. Phase 3: the modal menu engine (state machine, dispatcher, keybindings, status bar item).
4. Phase 4: the webview that shows the menu, with the list view.
5. Phase 5: the keyboard view, with the QWERTY and BÉPO layouts, and the removal of the proof of concept.
6. Phase 6: the documentation and the release preparation.

## Context

The Kakoune plugin (`abc-kak/rc/abc-modes.kak`) declares the user modes `abc-select`, `abc-transform`, `abc-select-inside`, `abc-select-around` and `abc-voicing`. The VS Code extension has the same commands but only in the command palette or behind user keybindings (`vscode-extension/src/selectorCommands.ts`, `vscode-extension/src/transformCommands.ts`).

A proof of concept (`vscode-extension/poc/keymap-keyboard.html`, a static page) was built, reviewed and approved. It fixes the keymap, the layouts and the look of the keyboard view. Phase 5 deletes it once the view is ported.

A spike showed that no extension can follow the held modifiers. A throwaway extension bound `shift`, `alt`, `ctrl` and `cmd` alone, and then `shift shift`, `alt alt` and `shift+alt`, to a logging command. Pressing the modifiers on the keyboard of the author produced no event. VS Code gives keybindings no modifier-only press and no key-up event, and the Vim fork receives keys through the same two inputs (contributed keybindings and the `type` command). Moving the focus to a webview to read the modifiers was rejected, because the focus must stay in the editor. The consequence is that the keyboard view draws the four layers of every key at once.

## Decisions already taken

- Entry keys are `h` (select) and `k` (transform) in the Normal and Visual modes of VSCodeVim. They override the Vim motions `h` and `k`. Because VS Code keybindings are static, the extension contributes default keybindings for the commands `abc.menu.select` and `abc.menu.transform`, and the user remaps them in `keybindings.json`.
- The groups `i`, `a` and `g` are nested menus. The menu closes after one command. The count is typed inside the transform menu, and a bound digit wins over the count (`g 2` is drop 2, and `5 g c` is a close voicing with 5 notes).
- The mode switch keys are `<`, `>` and Tab. In the select menu `1` selects the top note and `t` is its alias.
- The default keymap is one data file, overridable by the setting `abc.keymap`. The keys use the Kakoune notation extended with modifiers: `<a-t>`, `<c-up>`, `<c-S-up>`.
- The panel opens beside the editor and every time a menu opens or the mode switches (the setting `abc.menuView.autoOpen` defaults to `true`). The settings `abc.keyboardLayout` (`qwerty` or `bepo`), `abc.keyboardGeometry` (`staggered` or `ortholinear`) and `abc.keyboardIsoKeys` choose what the keyboard view draws. There is no automatic detection of the layout.
- The layouts are generated from the macOS layouts `U.S.` and `bépo 1.1`. No other layout is included now.
- The proof of concept is deleted after the port (the last step of phase 5).
- Commits are named after the module, for example `keymap: add the keymap data and its resolver`.

## Phase 1: keymap data, loader and resolver

Because the engine, the list view and the keyboard view all read the same keymap, we first need one typed tree and one resolver that do not depend on `vscode`.

Files created in one bash command, all under `vscode-extension/src/keymap/`: `types.ts`, `defaultKeymap.ts`, `notation.ts`, `loadKeymap.ts`, `resolve.ts`, `validate.ts`, `keymap.spec.ts`; and `vscode-extension/scripts/checkDefaultKeymap.ts`.

Types in `types.ts`:

```lua
type ActionKind = "selector" | "transform" | "command" | "mode"
type CountTemplate = { count: { default: number, multiplier: number } }
type ArgTemplate = string | number | boolean | null | CountTemplate
type Leaf = { type: "leaf", label: string, short?: string, category: string, action: { kind: ActionKind, name: string, args: ArgTemplate[] }, isNew?: boolean }
type Group = { type: "group", label: string, short?: string, category: string, children: Record<string, KeymapNode> }
type KeymapNode = Leaf | Group
type Keymap = { select: Group, transform: Group }
type KeymapOverride = { select?: Record<string, Partial<Leaf> | null>, transform?: Record<string, Partial<Leaf> | null> }
```

- The field `short` is the name that fits a keyboard cell (about ten characters). When it is absent, the keyboard view uses `label`.
- A `mode` action has the names `select`, `transform` and `toggle`.

Notation in `notation.ts`:

```lua
type Notation = { key: string, ctrl: boolean, alt: boolean, shift: boolean }
parseNotation(text: string): Notation | undefined
formatNotation(n: Notation): string
```

- A text of one character is a plain key, including `<` and `>` (`o`, `O`, `+`, `<`).
- A longer text must be `<` modifiers `-` key `>`. The modifiers are `a-` (Alt) and `c-` (Ctrl), and `S-` (Shift) is allowed only before a named key. The named keys are `up`, `down`, `left`, `right`, `tab`, `esc` and `bs`. The key after the modifiers is a single character or a named key. So `<a-t>`, `<a-T>`, `<c-up>` and `<c-S-up>` are valid, and `<S-t>`, `<x>` and `<a->` are not. An uppercase letter encodes the Shift key.

Default data: `defaultKeymap.ts` is the keymap of the appendix, with its short names and the `isNew` marks. It also holds the three mode leaves in both groups: `<` (mode `select`), `>` (mode `transform`) and `Tab` (mode `toggle`), labelled "go to select mode", "go to transform mode" and "switch mode". The `tab` named key writes `Tab` as `<tab>` in the data.

Functions:

- `mergeKeymap(defaults: Keymap, override: KeymapOverride): { keymap: Keymap, errors: string[] }`, in `loadKeymap.ts`. It deep-merges group paths, lets a leaf replace a group, lets a `null` delete a node, and reports errors instead of throwing (the parse module and the editor never throw outside the request and response cycle).
- `resolveKey(group: Group, path: string[], key: string): KeymapNode | undefined`, in `resolve.ts`.
- `expandArgs(args: ArgTemplate[], count: number | undefined): unknown[]`, in `resolve.ts`. A `CountTemplate` becomes `(count ?? default) * multiplier`.
- `validateKeymap(keymap: Keymap): string[]`, in `validate.ts`. It reports invalid notation, empty groups, a missing `action.name`, a `mode` action with an unknown name, a `count` template on an action that is not a transform, and two keys of one group with the same parsed notation.

Imports: `resolve.ts`, `loadKeymap.ts` and `validate.ts` import types from `types.ts` and `parseNotation` from `notation.ts`. Nothing imports `vscode`. The setting `abc.keymap` has the shape of `KeymapOverride`; for example `{ "transform": { "d": { "label": "drop 2", "category": "voicing", "action": { "kind": "transform", "name": "dropVoicing", "args": ["drop2"] } } } }`.

Build-time check in `vscode-extension/scripts/checkDefaultKeymap.ts` (a script, not a test, and outside the `tsc` project so it may import from the other packages):

- Because a leaf names its selector, transform or command as a string, a rename of the real function would leave a dead key in the menu. The script walks the default keymap and fails the build with the list of offending keys when it finds one.
- Every leaf of kind `selector` must resolve with `lookupSelector` (imported from `../../abc-lsp-server/src/selectorLookup`), and every leaf of kind `transform` must resolve with `lookupTransform` (imported from `../../editor/src/runner/transformLookup`). If the `ABCContext` import of `transformLookup` does not load under `tsx`, a list of the transform names in a fixture file replaces the lookup.
- Every leaf of kind `command` must be named in `contributes.commands` of `package.json`, except the built-in `undo` and the `abc.menu.*` commands that phase 3 adds.
- The script also runs `validateKeymap` on the default keymap and fails on any error.
- The `build` script of `vscode-extension/package.json` runs it first: `tsx scripts/checkDefaultKeymap.ts && tsc -p ./ && node esbuild.js`. Only the default keymap is checked. A user's `abc.keymap` is the user's responsibility, and the runtime reports only the structural errors of `validateKeymap`.

Testing, example-based cases:

- `parseNotation("<a-O>")` gives `{ key: "O", ctrl: false, alt: true, shift: false }`, `parseNotation("<c-S-up>")` gives ctrl and shift with the key `up`, `parseNotation("<")` gives the plain key `<`, and `<x>`, `<S-t>` and `<a->` give `undefined`.
- An override that adds `transform.d` is found by `resolveKey`.
- A `null` override removes `select.c`.
- A leaf that replaces the group `transform.g` is accepted.
- `expandArgs([{count:{default:4,multiplier:1}}], 5)` gives `[5]`, and `expandArgs([{count:{default:1,multiplier:12}}], undefined)` gives `[12]`.
- The default keymap gives no `validateKeymap` error.
- Two keys `<a-t>` and `<a-t>` of one group give an error.

Testing, properties (fast-check is a dev dependency of the repository root):

- `formatNotation(parseNotation(k))` equals `k` for every valid notation.
- `mergeKeymap(d, {})` equals `d`.
- Merging the same override twice gives the same result as merging it once.
- `resolveKey` never throws for any path and key.
- `expandArgs` of a list without `CountTemplate` returns the list unchanged for any count.

## Phase 2: voicing retrofit and settings

Because the keymap needs voice counts other than 4, and users with their own keybindings need them too, the three preset commands accept an argument.

Files created in one bash command: `vscode-extension/src/voicingArgs.ts` and `vscode-extension/src/voicingArgs.spec.ts`.

- `voicingArgs.ts` exports `VoicingArgs` (`{ voices?: number }`) and `resolveVoices(args: unknown): number | undefined`. It has no imports. The function returns 4 for `undefined` or an object without `voices`, the number when it is 4, 5 or 6, and `undefined` for anything else, including values that are not objects.
- `transformCommands.ts` imports both. In the `voicingPresets` loop (`abc.harmonizeClose`, `abc.harmonizeCluster`, `abc.harmonizeSpread`) each handler takes `args?: VoicingArgs`, calls `resolveVoices`, shows `vscode.window.showErrorMessage("Voice count must be 4, 5 or 6")` and returns when the result is `undefined`, and otherwise calls `applyTransform(client, "harmonizeVoicing", [voicing, voices, null], statusBarItem)`.
- `abc.harmonizeVoicing` (the prompting command) and the drop commands are unchanged. The built-in `undo` needs no registration.
- Settings added to the `configuration` block of `vscode-extension/package.json`: `abc.keymap` (object, default `{}`, the shape of `KeymapOverride`), `abc.keyboardLayout` (enum `qwerty`, `bepo`; default `qwerty`) and `abc.keyboardGeometry` (enum `staggered`, `ortholinear`; default `staggered`).
- Keybinding example for users, documented in phase 6: `{ "key": "ctrl+alt+5", "command": "abc.harmonizeClose", "args": { "voices": 5 } }`.

Testing, example-based cases: `resolveVoices(undefined)` and `resolveVoices({})` give 4; `{ voices: 5 }` gives 5; `{ voices: 3 }`, `{ voices: 7 }`, `{ voices: "5" }`, `{ voices: 4.5 }`, `null` and `"x"` give `undefined`. A package check test reads `package.json` and verifies the three settings, their types, enum values and defaults.

Testing, properties: for any value `v`, `resolveVoices({ voices: v })` gives a number only if `v` is 4, 5 or 6; the result is never a number outside 4 to 6.

## Phase 3: the modal menu engine

Because the engine must receive typed keys without competing with the `type` handler of VSCodeVim (only one extension can override `type`), the menu uses contributed keybindings, which win over `type`. Because the keyboard focus stays in the editor, the engine never sees a held modifier, only complete key presses.

Files created in one bash command, under `vscode-extension/src/menu/`: `menuState.ts`, `menuState.spec.ts`, `keybindingKeys.ts`, `keybindingKeys.spec.ts`, `modalMenu.ts`, `dispatch.ts`, `keybindingsCoverage.spec.ts`; and `vscode-extension/scripts/generateMenuKeybindings.ts`.

Pure state machine in `menuState.ts` (no `vscode` import):

```lua
type MenuState = { open: boolean, mode: "select" | "transform", path: string[], count: string }
type MenuInput = { notation: string }
type MenuEffect = { kind: "none" } | { kind: "run", leaf: Leaf, count: number | undefined } | { kind: "error", message: string }

openMenu(mode): MenuState
step(state: MenuState, keymap: Keymap, input: MenuInput): { state: MenuState, effect: MenuEffect }
```

Rules of `step`, in order:

1. `<esc>` closes the menu. `<bs>` removes the last count digit, or else the last path element, or else closes.
2. A leaf of kind `mode` (`<`, `>` and `Tab` by default) switches the mode, clears the path and keeps the count. The name `toggle` switches to the other mode.
3. A key bound at the current path wins. A group extends the path, and a leaf produces `run` and closes the menu.
4. An unbound digit in transform mode appends to the count, up to three digits. In select mode an unbound digit does nothing.
5. Any other unbound key produces `none`, and the menu stays open.

Mapping of notations to keybindings, in `keybindingKeys.ts` (no `vscode` import):

- `toVsCodeKey(notation: string): string | undefined` converts a notation to the `key` string of a keybinding: `a` to `a`, `A` to `shift+a`, `<a-t>` to `alt+t`, `<a-T>` to `alt+shift+t`, `<c-up>` to `ctrl+up`, `<c-S-up>` to `ctrl+shift+up`, `<tab>` to `tab`, `<esc>` to `escape`, `<bs>` to `backspace`, and symbols to their US spelling (`{` to `shift+[`).
- `MENU_KEY_SUPERSET: string[]` lists the notations that get a keybinding: the letters and their Shift variants, `<a-letter>` and `<a-LETTER>`, the digits, the ASCII symbols, the four arrows with `<c-...>` and `<c-S-...>`, `<tab>`, `<esc>` and `<bs>`. A key with no US spelling, such as an accented letter, has no default keybinding, because VS Code does not accept it in a contributed keybinding. The user adds it to `keybindings.json`, and the warning gives the entry.

VS Code glue in `modalMenu.ts`:

- `registerModalMenu(context, client, statusBarItem)` is called from `extension.ts` after `registerTransformCommands`. It registers `abc.menu.select`, `abc.menu.transform`, `abc.menu.close` and `abc.menu.key` (argument `{ notation: string }`).
- It sets the context key `abc.modeMenuOpen` on open and close, and closes the menu when the active editor changes.
- It loads the keymap with `mergeKeymap(defaultKeymap, config.get("abc.keymap"))`, shows the validation errors once with `showWarningMessage`, and reloads when the configuration changes.
- A second status bar item shows the state, for example `select > g > 5`. The existing item that counts selections stays.
- After every `step` and every keymap reload it calls `updateMenuView` (phase 4) when that function exists, through a callback parameter, so phase 3 does not depend on phase 4.

Keybindings in `package.json`:

- Entry: `h` runs `abc.menu.select` and `k` runs `abc.menu.transform`, with the `when` clause `editorLangId == abc && editorTextFocus && !abc.modeMenuOpen && (vim.mode == 'Normal' || vim.mode == 'Visual' || vim.mode == 'VisualLine')`. Without VSCodeVim there is no default entry key, because `h` and `k` would otherwise stop typing in every ABC file; the user binds `abc.menu.select` and `abc.menu.transform` in `keybindings.json`.
- Menu keys: one binding for each notation of `MENU_KEY_SUPERSET`, with the `when` clause `abc.modeMenuOpen && editorTextFocus && editorLangId == abc` and the command `abc.menu.key` with `{ "notation": ... }`. Because of that scope, a focus in the terminal, the explorer or the command palette types normally even if a menu was left open. The script `generateMenuKeybindings.ts` writes this block into `package.json`, and the build runs it, so the superset is never edited by hand. The generator only produces the defaults; nothing prevents the user from changing a binding afterwards.

How the user changes bindings:

- Changing what a key does needs only the setting `abc.keymap`. It works for every key of the superset, because the keybinding for that key already forwards it to the engine.
- Changing which key opens a menu needs `keybindings.json`: the user rebinds `abc.menu.select` or `abc.menu.transform`.
- Using a key outside the superset needs one entry in `keybindings.json`: `{ "key": "...", "command": "abc.menu.key", "args": { "notation": "..." }, "when": "abc.modeMenuOpen" }`. Because VS Code has no catch-all keybinding, this entry is the only way. When `abc.keymap` binds a key outside the superset, `modalMenu.ts` shows a warning with this exact snippet, so the user is never left with a silent dead key.

Dispatcher in `dispatch.ts`:

- `runLeaf(leaf: Leaf, count: number | undefined, deps)` expands the arguments with `expandArgs` (phase 1).
- A `selector` calls `applySelectorByName(client, name, args, statusBarItem)`, extracted in `selectorCommands.ts` from the block that each selector command repeats. The existing commands call it and their behavior does not change.
- A `transform` calls `applyTransform`, exported from `transformCommands.ts` (private today).
- A `command` calls `vscode.commands.executeCommand(name, ...args)`.

Known limit: keys reachable only through AltGr on some layouts may not match a keybinding written for another layout. The acceptance test is that, with BÉPO, `k`, then `<`, then `>` switch the modes. The macOS system shortcuts that use the Ctrl arrow chords (Mission Control) are the user's to disable.

Testing, example-based cases for `menuState.spec.ts`:

- `c` in the select menu produces `run` with `selectChords` and closes.
- In transform mode, `5`, `g`, `c` produces `harmonizeVoicing` with count 5.
- `g`, then `2` produces `dropVoicing` with `drop2` and no count.
- In select mode, `1` produces `selectNthFromTop` with `[0]`.
- `<esc>` closes, and `<bs>` at the root closes.
- `<` in transform mode switches to select with the path cleared and the count kept.
- An unbound key keeps the menu open with `none`, and a fourth count digit is ignored.

Testing, example-based cases for `keybindingKeys.spec.ts` and `keybindingsCoverage.spec.ts`: the conversions above; every notation of the default keymap is in the superset and has a binding in `package.json`; a key outside the superset yields the warning with the snippet.

Testing, properties:

- Every key sequence ends with a count of at most three digits.
- Every leaf of the default keymap is reachable by a key sequence built from the tree.
- After a `run` effect, `open` is false.
- `toVsCodeKey(n)` is injective on the superset: two notations never share a key string.

The existing runner `src/test/suite/index.ts` does not work with the installed `glob`, so the tests are run with a runner that adds only `menu.test.js`.

## Phase 4: the shared webview and the list view

Because the list and the keyboard are two views of the same state, one webview with one message protocol serves both. Phase 4 builds the webview and the list view, and phase 5 adds the keyboard view. A quick pick is not used, because it takes the keyboard focus from the editor. The webview opens with `preserveFocus: true`.

Files created in one bash command. Under `vscode-extension/src/menu/`: `categories.ts`, `menuViewModel.ts`, `menuViewModel.spec.ts`, `viewMessages.ts`, `menuView.ts`, `menuViewHtml.ts`. Under `vscode-extension/webview/`: `menuView.ts`, `menuView.css`, `menuView.spec.ts`.

Pure view model in `menuViewModel.ts` (no `vscode` import):

```lua
type ViewRow = { notation: string, label: string, short: string, category: string, isGroup: boolean, isNew: boolean, action: string }
type ViewModel = { mode: "select" | "transform", open: boolean, breadcrumb: string[], count: string, rows: ViewRow[] }

buildViewModel(keymap: Keymap, state: MenuState): ViewModel
```

- `rows` are the children of the group at `state.path`, in the order of the keymap, and `short` is `node.short ?? node.label`.
- `breadcrumb` holds the labels of the groups along the path, starting with the label of the mode.
- A path that no longer resolves, for example after a change of `abc.keymap`, gives the root rows and an empty breadcrumb. Inside a group the rows also list the mode keys of the root, because they work there. The function never throws. The label of a group is shown without its ellipsis in the breadcrumb.
- `categories.ts` exports `CATEGORY_NAMES` and `CATEGORY_ORDER` (the ids of the appendix, in that order), moved from the proof of concept. Phase 5 reads the same table.

Messages in `viewMessages.ts`:

```lua
type ToWebview = { type: "model", model: ViewModel }   -- phase 5 adds the optional field keyboard: KeyboardModel
type ToExtension = { type: "press", notation: string } | { type: "ready" }
```

The webview sends `ready` on load and the extension answers with the current model. A click on a row sends `press`, which the extension feeds to the same `step` function as a key press.

Extension side:

- `menuViewHtml.ts` exports the pure `renderWebviewHtml(parts: HtmlParts): string` and `makeNonce()`, and `menuView.ts` builds the parts from the webview, for both locations below. The page has a content security policy with the nonce, scripts only from `dist/webview/`, and no inline script. Colors come from the `--vscode-*` theme variables, with a fixed accent color for each category.
- `menuView.ts` exports `registerMenuView(context, onPress)` and `updateMenuView(model, keyboard?)`. It registers `abc.menu.showView` and `abc.menu.hideView`.
- The setting `abc.menuView.location` (enum `beside`, `panel`; default `beside`) chooses where the view lives. With `beside` the view is a webview panel created with `vscode.window.createWebviewPanel("abcMenuView", "ABC keys", { viewColumn: vscode.ViewColumn.Beside, preserveFocus: true }, { enableScripts: true, retainContextWhenHidden: true, localResourceRoots: [dist/webview] })`. With `panel` it is a webview view in the bottom panel, contributed under `contributes.viewsContainers.panel` (id `abcKeys`) and `contributes.views` (id `abcMenuView`), implemented by a `vscode.WebviewViewProvider`. The bottom panel is as wide as the window, which suits the keyboard view of phase 5. Both locations use the same page (`renderWebviewHtml`) and the same messages. Because opening a view in the bottom panel takes the focus, the `panel` location never opens by itself: the user opens the tab ABC keys once, and it keeps its content (`retainContextWhenHidden`).
- The setting `abc.menuView.autoOpen` (boolean, default `true`) opens the beside view every time a menu opens or the mode switches, and creates it again if the user closed it. With `false` the user opens it with `abc.menu.showView`. The view stays open when the menu closes and shows the root of the last mode as a reference.
- `modalMenu.ts` (phase 3) passes `updateMenuView` as its callback.
- A model sent before the page has loaded would be lost, so the extension sends nothing until the webview says `ready`, and then sends the current model. A click on a row while the menu is closed first opens the mode that the view shows, and the focus goes back to the last ABC editor before a click is handled, because a webview has no active editor, so a selector or a transform could not run, and because the keys of the menu only work where the editor has the focus. Each page (the beside panel and the bottom view) has its own ready flag, so one cannot hide the state of the other, and a message of the wrong shape is ignored. The menu does not close when the focus moves to a webview, or when the focus comes back to the document in which the menu was opened: it closes only when another document becomes active.

Webview script in `webview/menuView.ts`: it renders the breadcrumb, the count, and the rows grouped by category, with the key in the Kakoune notation, the label, the "new" tag and the group marker. `vscode-extension/esbuild.js` gets one more entry point that bundles the script for the browser and copies the CSS to `dist/webview/`, and `webview/tsconfig.json` type checks the script with the DOM library; one `npm run build` stays enough.

Testing, example-based cases for `menuViewModel.spec.ts`:

- At the root of select mode, the rows start with the digits and include the group `i`.
- After `g` in transform mode, the breadcrumb is `["transform", "voicing menu (count = voices)"]` and the rows are `2`, `3`, `4`, `c`, `k`, `s` and the mode keys `<`, `>` and `<tab>`.
- A count of `5` appears in the model.
- A path that does not resolve falls back to the root rows.

## Phase 5: the keyboard view

Because the panel cannot see the held modifiers, every cap is a grid of four cells, one for each layer: Shift top left, AltGr and Shift top right, base bottom left, AltGr bottom right. Each cell shows the character that the layer types and the short name of its binding.

Files created in one bash command. Under `vscode-extension/src/keyboard/`: `layouts.ts`, `keyboardModel.ts`, `keyboardModel.spec.ts`. Under `vscode-extension/webview/`: `keyboardView.ts`, `keyboardView.spec.ts`. Under `vscode-extension/scripts/`: `generateLayouts.swift`.

Layout data in `layouts.ts`:

```lua
type KeyCap = [base: string, shift: string, altgr: string, altgrShift: string, flags?: { iso?: true, dead?: boolean[] }]
type LayoutRow = { offset: number, keys: KeyCap[] }
type Layout = { id: "qwerty" | "bepo", rows: LayoutRow[] }
```

- `flags.dead` has four booleans, one for each layer, and a dead key types no symbol of its own, so it never matches a binding. `flags.iso` marks the keys that only ISO keyboards have, such as `$` and `ç` of BÉPO.
- `generateLayouts.swift` asks macOS what every key types, with `UCKeyTranslate`, for the four modifier states (none, Shift, Option, Option and Shift) of the layouts `com.apple.keylayout.US` and `com.apple.keyboardlayout.bepo.keylayout.bépo`, and writes `layouts.ts`. It uses the ISO keyboard type (41), so that the codes 10 and 50 are the ISO key and the key under Esc. A layer is dead when the press leaves a dead key state, and its character is what the dead key and the space bar type. The US layout has no ISO-only keys. The result is committed, so the build does not depend on macOS. It replaces the QWERTY Option layer that the proof of concept wrote from memory. Run it with `swift scripts/generateLayouts.swift > src/keyboard/layouts.ts`, and with `--list` it prints the installed layouts.
- A test checks the header of `layouts.ts` and that every row of each layout has the expected number of keys.

Pure model in `keyboardModel.ts` (no `vscode` import):

```lua
type KeyboardOptions = { layout: "qwerty" | "bepo", geometry: "staggered" | "ortholinear", iso: boolean }
type LayerView = { level: 0 | 1 | 2 | 3, symbol: string, state: "bound" | "unbound" | "dead" | "count", row?: ViewRow, notation: string }
type CapView = { row: number, col: number, offset: number, layers: [LayerView, LayerView, LayerView, LayerView] }
type KeyboardModel = { layout, geometry, caps: CapView[][], tray: ViewRow[] }

buildKeyboardModel(keymap: Keymap, state: MenuState, options: KeyboardOptions): KeyboardModel
rowOffset(layout: Layout, rowIndex: number, options: KeyboardOptions): number
```

- Resolution of a layer: the symbol that the layer types wins when it is bound at the current path. Otherwise, a layer at level 2 or 3 resolves to the Alt chord of the physical key, which is `<a-x>` with the character `x` of the same key at level 0 or 1. A dead layer's symbol never matches a binding, but its Alt chord can, because a keybinding fires on the physical key whatever the key types. The notation of a layer is the key as the keymap spells it, so that the menu finds the key again when the user wrote the modifiers in another order.
- `count`: in transform mode, an unbound digit at level 0 or 1 has the state `count`.
- `rowOffset`: staggered geometry gives the offset of each row of the layout (0, 0.5, 0.75 and 1.25 in units of a cap). Ortholinear geometry gives 0 for the first row and 1 for the others, and a leading ISO key takes the column on the left of that. When `iso` is false the keys flagged `iso` are left out.
- `tray`: the notations of the current group that no layer of any cap resolves to, which are the mode keys when the layout does not type `<` or `>`, `Tab`, and the Ctrl chords such as `<c-up>` and `<c-S-up>`.

Webview, in `keyboardView.ts`:

- It draws the tray above the board, the four-cell caps, the category chips, the detail strip, and the controls. A cell with a binding is tinted with its category color and has a colored top edge; an unbound cell shows only its faint character; a dead key is italic; the "new" tag sits beside the character; the count cells say "count".
- The detail strip shows the four layers of the hovered key, each with its layer name, symbol, full label, Alt chord, category and action.
- The controls are the Show selector (all layers, base, Shift, AltGr, AltGr+Shift; a single layer fades the other three), the "free keys" toggle that highlights the unbound cells, and the switch between list, keyboard and both. They live in the webview state (`vscode.setState`).
- A click on a cell sends `press` with the notation of that layer, like a row of the list.
- The cap width is computed from the webview width, with a minimum of 84 pixels and a height of 1.08 times the width. Below that minimum the board scrolls horizontally, and the list stays under it. The `beside` location is often narrower than the board needs, and that is the reason for the `panel` location of phase 4.
- The extension builds the model on every update from the settings `abc.keyboardLayout`, `abc.keyboardGeometry` and `abc.keyboardIsoKeys` (boolean, default `false`), and sends it in the `keyboard` field of the `model` message. The logic of resolution stays in the tested model, and the webview only draws.

## Risks

- The keybindings are written with the characters of a US keyboard and VS Code matches them through the layout, so on other layouts a shifted symbol or a digit may not fire. The author checks the acceptance keys (`k`, `<`, `>` and the digits of the select menu) on BÉPO, and the user adds entries to `keybindings.json` for the keys that do not.
- On Windows and Linux, AltGr is Ctrl+Alt, so the Alt chords and the AltGr symbols may collide. The layouts are read from macOS, and the AltGr layers of other systems may differ. The plan does not claim support outside macOS for the Alt layer, and the documentation says so.
- The keyboard view needs about 1150 pixels. The `panel` location of phase 4 gives that width, and the `beside` location scrolls horizontally.
