## 1. Why this work exists

Because the iReal Pro import path performs seventeen successive regular expression
replacements over one raw string before anything is tokenized, structural
information has to be smuggled through that string and recovered from it later,
and that recovery keeps failing in new ways. Six distinct defects traced to this
one cause in a single working session:

- An unmatched `{` fused onto the chord that followed it, so that chord was dropped.
- Vertical spacer characters (`Y`) leaked into chord text.
- Barlines were written into bar content strings, so the step that joins bars with
  separators doubled them, producing `:| |`, `| |:` and `:| |:`.
- Bars with no content were emitted, printing a stray barline and shifting the
  four-bars-per-line layout for the rest of the chart.
- A section label immediately before a repeat section was given a bar of its own,
  leaving the letter in a chordless measure and shifting every following line.
- A section label whose letter is one the cleanup passes delete (`f`, `l`, `s`,
  `Y`, `U`, `S`, `Q`) decays to an empty sentinel and is dropped silently.

Three further defects from the same session were genuine gaps in knowledge of the
format rather than consequences of the architecture (the `-` minor key suffix, the
`alt` quality, the `-^` minor-major quality), and those would have occurred under
any design. The six above would not.

This repository already contains the infrastructure these six defects call for: a
cursor-based scanner pattern in `parse/parsers/scan.ts`, a parser in
`parse/parsers/parse.ts`, an error reporter in `parse/parsers/ErrorReporter.ts`,
and a context object in `parse/parsers/Context.ts`. The iReal import path uses
none of it. The only file under `parse/ireal/` that references `ABCContext` is
`exportToIreal.ts`, which runs in the opposite direction.

## 2. What the current implementation does, and why it keeps producing the same class of bug

The present pipeline, per song:

```
irealb:// link
  -> fields.ts parsePlaylistLink          (split song fields)
  -> scramble.ts unscramble               (de-obfuscate chord data -> raw grid text)
  -> gridAnnotations.ts cleanGridText     (17 regex passes over the whole string)
  -> gridNotation.ts textToGridTokens     (split on "|" and whitespace into cells)
  -> importFromIreal.ts gridTokensToAbcxBody  (cells -> ABCx text)
  -> AbcxToAbcConverter convertAbcxToAbc  (ABCx -> ABC)
```

Two properties of that shape cause the defect class:

Because `cleanGridText` edits one flat string, every pass has whole-string scope.
A pass meaning "delete a stray fermata marker" is written as "delete every
lowercase `f` in the chart", which can and does hit characters that belong to
something else. The passes that delete bare `f`, `l`, `s`, `Y`, `U`, `S` and `Q`
are all of this kind.

Because `textToGridTokens` is a cell splitter rather than a scanner, it has no
cursor, no token positions, no longest-match discipline, and no error channel. It
compares each whitespace-delimited cell against a few literals and, failing those,
hands the cell to the chord parser; a cell the chord parser rejects is discarded
with no record. Content loss is therefore invisible by construction.

## 3. Target architecture

```
irealb:// link
  -> fields.ts parsePlaylistLink          (unchanged)
  -> scramble.ts unscramble               (unchanged)
  -> gridScanner.ts scanGrid              (raw grid text -> GridToken[] with positions)
  -> gridParser.ts parseGrid              (GridToken[] -> IrealChart AST)
  -> gridToAbcx.ts chartToAbcxBody        (AST -> ABCx tune body text)
  -> AbcxToAbcConverter convertAbcxToAbc  (unchanged)
```

Three properties this shape must have, each one closing off one of the six
defects above:

Every character of the input belongs to exactly one token. Concatenating the
lexemes of the token stream in order reproduces the input exactly. A character
the grammar does not recognize produces a token of type `UNKNOWN` carrying its
position, and an entry in the error reporter; it is never discarded. Content loss
becomes a detectable condition rather than a silent one.

Structure lives in the tree, not in strings. A barline is a property of the
boundary between two bars; a section label is a property of a section; a repeat
is a property of a span of bars. No consumer needs to inspect text to recover any
of these, so no consumer can get that inspection wrong.

Resolution happens as tree transformation. The constructs that currently splice
text (a repeat section duplicated inline, a coda jump reordering the chart) become
operations on bars and sections.

## 4. Grammar of the iReal Pro grid language, as currently understood

This section records what a working session established against a real library of
657 charts, so the implementer does not have to rediscover it. The grid text
described here is the output of `unscramble`, which has already replaced the
obfuscated sequences `Kcl` with `| x`, `LZ` with ` |`, and `XyQ` with three
spaces.

Cells and separators:

- A chord cell, in iReal Pro's own chord dialect, not ABC's. Minor is `-` (`C-7`),
  major seventh is `^` (`C^7`), half-diminished is `h` (`Ch7`), diminished is `o`
  (`Co7`), augmented is `+`. A suspended chord writes its extension before the
  word (`G7sus`, `A9sus`), and a bare `sus` means sus4. An altered dominant
  writes `alt` after its extension (`C7alt`). Minor-major seventh is the combined
  symbol `-^` (`C-^7`), which must be matched before either `-` or `^` alone. A
  slash bass follows a `/` (`C-7/F`).
- `|` separates bars.
- `n` means no chord, rendered N.C.
- `x` means this bar repeats the previous bar.
- `r` means this bar repeats the previous two bars. Present in real charts, for
  example "Hindsight". Not implemented today.
- `p` means this cell holds the same chord as the previous cell. Present in real
  charts, for example "Captain Marvel", where it appears doubled as `pp`. Not
  implemented today.
- `,` pads a cell to indicate a held chord and carries no further meaning.

Structure:

- `{` opens a repeated section and `}` closes it. A chart may open one and never
  close it, for example "Perhaps", so an unclosed open must be tolerated.
- `N1`, `N2` and further numbered markers introduce the first, second and later
  endings of a repeated section. iReal Pro writes later endings outside the
  closing brace.
- `[` and `]` bound sections.
- `*A`, `*B`, `*C`, `*D`, `*i`, `*v` label a section. Across the sample library
  the letters observed were `A` 746 times, `B` 507, `C` 188, `i` 72, `D` 23 and
  `v` twice. A label is commonly glued directly onto the chord that follows it,
  and onto a time signature, as in `{*AT44C^7`.
- `T` followed by two digits is a time signature, `T44` being four four. It can
  appear anywhere a section begins, not only at the start of a chart.
- `S` marks a segno, `Q` a coda, and `U` a part marker.
- `Z` ends the chart.

Annotations and decoration:

- `<` and `>` bound a text annotation. The text may carry a leading size code of
  `*` and two digits, as in `<*64Open Feel>`. The sample library holds 168 such
  annotations across 50 charts, including `D.C. al Coda`, `D.S. al coda`, `Fine`,
  `Ending`, `Solos`, `Open for solos`, `solos on AABA`, `3x`, `4x`, `rit.....`,
  `Fade`, `Even 8's` and `Optional Bb pedal in A sections`. Several of these are
  structural rather than decorative and are discarded entirely today.
- `(` and `)` bound an alternative chord, which the current implementation drops.
- `f` marks a fermata, `s` a cue-sized chord, `l` a layout hint, and `Y` vertical
  spacing. All four are single lowercase letters with no delimiters, which is why
  deleting them by regular expression over the whole string is unsafe.

## 5. New and retired files, with the types each one needs

New files, all under `parse/ireal/`:

- `gridTokens.ts`. Declares `GridTT`, the token type enumeration, and `GridToken`,
  an interface carrying `type: GridTT`, `lexeme: string` and `position: number`.
  Mirrors the shape of `ChordToken` and `ChordTT` in
  `parse/music-theory/types.ts`, which are the closest existing precedent for a
  small token set local to one module.
- `gridScanner.ts`. Exports `scanGrid(source: string, ctx: ABCContext): GridToken[]`.
  Imports `ABCContext` from `../parsers/Context` and reports through
  `ctx.errorReporter`, whose type `AbcErrorReporter` comes from
  `../parsers/ErrorReporter`.
- `gridScanner.pbt.generators.ts` and `gridScanner.pbt.spec.ts`. Follow the naming
  and structure of `parse/analyzers/info-line-analyzer.pbt.generators.ts` and its
  matching spec, which is the established pattern in this repository for a
  generator module paired with a property specification.
- `gridScanner.spec.ts`. Example-based tests, including one per construct named in
  section 4 and one per defect listed in section 1.
- `gridAst.ts`. Declares the tree types given in section 7.
- `gridParser.ts`. Exports `parseGrid(tokens: GridToken[], ctx: ABCContext): IrealChart`.
- `gridParser.spec.ts`.
- `gridToAbcx.ts`. Exports `chartToAbcxBody(chart: IrealChart): string`.
- `gridToAbcx.spec.ts`.

Existing files to change:

- `importFromIreal.ts`. `buildSongAbcxText` currently calls `textToGridTokens` and
  `gridTokensToAbcxBody` at lines 294 to 296. It should instead call `scanGrid`,
  `parseGrid` and `chartToAbcxBody`. `buildSongAbcxText` needs an `ABCContext` to
  pass down; `importIrealLinkToAbcx` should construct one and thread it through.
  Once Phase 3 is complete, `cellText`, `splitIntoBars`, `isRepeatBar`,
  `hasMusicalContent`, `compactImmediateRepeats`, `barlineBetween`, `renderBars`
  and `gridTokensToAbcxBody` are all superseded and should be deleted.
- `chordShorthand.ts`. Keep as the chord parser for iReal Pro's dialect. It must be
  called on a chord token produced by the scanner rather than on arbitrary split
  text. Do not substitute `music-theory/scanChordSymbol.ts`, which implements
  ABCx's dialect (`m7`, `maj7`, `ø`) and not iReal Pro's (`-7`, `^7`, `h7`).

Existing files to retire:

- `gridAnnotations.ts`. Every pass in it becomes either a scanner rule or a tree
  transformation. Delete the file once Phase 3 passes the invariants in section 9.
  Its companion `gridAnnotations.spec.ts` goes with it; any case it covers that is
  not already covered by a scanner or parser test must be ported first.
- `gridNotation.ts`. `textToGridTokens` and `gridTokensToText` are superseded by
  the scanner. `GridToken` moves to `gridTokens.ts` in a richer form. Check for
  importers outside `parse/ireal/` before deleting.

## 6. Phase 1: scanner, token types, and property-based tests

Deliverables: `gridTokens.ts`, `gridScanner.ts`, `gridScanner.spec.ts`,
`gridScanner.pbt.generators.ts`, `gridScanner.pbt.spec.ts`, and a verification run
showing token-level coverage across the sample library.

Token types to declare in `GridTT`, one per construct in section 4:

```
CHORD, NO_CHORD, REPEAT_ONE_BAR, REPEAT_TWO_BARS, SAME_CHORD,
BAR, SECTION_OPEN, SECTION_CLOSE, REPEAT_OPEN, REPEAT_CLOSE, ENDING,
SECTION_LABEL, TIME_SIGNATURE, ANNOTATION, ALTERNATIVE_CHORD,
SEGNO, CODA, PART_MARKER, FERMATA, SMALL, LAYOUT, SPACER, PAD, END,
WHITESPACE, UNKNOWN
```

Scanner structure, following `parse/parsers/scan.ts`:

```
scanGrid(source, ctx)
  cursor = 0
  tokens = []
  while cursor < source.length
    for each rule in RULES            // order matters, see below
      if rule matches at cursor
        push token (type, lexeme, position = cursor)
        cursor += lexeme.length
        continue outer loop
    // no rule matched
    push token (UNKNOWN, source[cursor], cursor)
    ctx.errorReporter.report(...)     // never discard
    cursor += 1
  return tokens
```

Rule ordering requirements, each of which has already caused a defect once:

- `-^` is tried before `-` and before `^`, so the minor-major symbol is not split.
- `sus4` and `sus2` are tried before `sus`.
- `T` followed by two digits is tried before any rule that could consume `T`.
- `N` followed by a digit is tried before the part marker rule that consumes `S`,
  `U` and `Q`, and before any chord rule.
- A section label (`*` followed by one word character) is tried before the
  annotation size code inside `<...>`, which is scanned as part of the annotation.
- The annotation rule consumes from `<` through the matching `>` as one token, so
  nothing inside it is scanned as grid content.
- The chord rule is tried before the single-letter decoration rules, so the `s`
  in `C7sus` and the `l` in `C7alt` are never taken as decoration.

Property-based tests, which are the central deliverable of this phase. Mirror the
generator-and-specification pairing used by
`parse/analyzers/info-line-analyzer.pbt.generators.ts`. The generator should build
a grid from a list of known token specifications and return both the rendered text
and the expected token list, so that properties can compare against an expectation
rather than only against themselves. Vary whitespace and gluing between cells,
because real charts glue labels, time signatures and chords together.

Properties to assert:

- Total coverage. Concatenating `token.lexeme` over the stream, in order, equals
  the input exactly. This is the property that makes silent content loss
  impossible, and the one that would have caught four of the six defects in
  section 1.
- Position integrity. Positions increase strictly, and each token's position plus
  its lexeme length equals the next token's position.
- Termination and total function. Scanning any string of printable ASCII returns
  without throwing.
- Grammar closure. For any grid the generator builds from the known grammar, no
  token has type `UNKNOWN`.
- Expectation match. For any grid the generator builds, the scanned token types
  equal the generator's expected token types.
- Stability. Rendering the token stream back to text and scanning again yields an
  identical stream.

Phase 1 acceptance: all properties hold; every construct in section 4 has an
example-based test; scanning all 657 charts in the sample library produces zero
`UNKNOWN` tokens, or a written list of the exact inputs that produce them with a
reason for each.

## 7. Phase 2: parser and abstract syntax tree

Tree types to declare in `gridAst.ts`. `ParsedChord` is imported from
`../music-theory/types`:

```
IrealChart
  sections: Section[]
  navigation: { segnoSectionIndex?, codaSectionIndex? }
  annotations: Annotation[]        // chart-level, e.g. D.C. al Coda

Section
  label?: string                   // "A", "B", "i"
  timeSignature?: { numerator: number; denominator: number }
  bars: Bar[]
  repeat?: Repeat

Repeat
  kind: "simple" | "endings"
  endings?: Ending[]               // kind === "endings"

Ending
  number: number                   // 1, 2, ...
  bars: Bar[]

Bar
  cells: Cell[]
  annotations: Annotation[]        // bar-level, e.g. <Solos>
  fermata: boolean

Cell
  kind: "chord" | "noChord"
  chord?: ParsedChord              // kind === "chord"
  small: boolean                   // the "s" cue-size marker
  alternative?: ParsedChord        // the "(...)" alternative chord

Annotation
  text: string
  position: number                 // source offset, for diagnostics
```

Resolution rules, performed as tree transformations rather than text splicing:

- A bar whose only cell is `REPEAT_ONE_BAR` takes a copy of the preceding bar's
  cells. The copy does not carry the preceding bar's label or annotations, because
  those belong to the bar that introduced them.
- A bar whose only cell is `REPEAT_TWO_BARS` takes copies of the two preceding
  bars, and therefore expands into two bars.
- A `SAME_CHORD` cell takes the chord of the preceding cell, or of the last cell of
  the preceding bar when it is first in its bar.
- A bar with no cells is not a bar. Drop it, and carry any label or annotation it
  holds onto the next bar that does have cells. This rule is what makes the
  phantom label bar and the empty bar defects impossible rather than merely fixed.
- `{` to `}` with no `ENDING` token inside becomes a `Section.repeat` of kind
  `simple`. The section's bars are stored once; they are not duplicated.
- `{` to `}` containing `ENDING` tokens, with further `ENDING` tokens after the
  closing brace, becomes a `Repeat` of kind `endings`, with the common bars in
  `Section.bars` and each ending's own bars in `Ending.bars`.
- An unclosed `{` is reported through the error reporter and treated as a section
  boundary, because a chart in the sample library has one and its chords must
  still import.
- `S`, `Q` and `U` record positions in `IrealChart.navigation` rather than
  reordering anything. The emitter decides how to express them.

Phase 2 acceptance: parsing all 657 charts produces zero thrown errors; the
multiset of chords in the tree, per chart, is equal to or larger than the multiset
the current implementation produces for that chart; example-based tests cover each
resolution rule and each defect in section 1.

## 8. Phase 3: emitter, and retiring the old path

`chartToAbcxBody` walks the tree and writes ABCx. Points settled by earlier work,
which must not be re-litigated by re-deriving them from text:

- The barline between two bars is a function of both bars. A section that closes a
  repeat where the next opens one is the single symbol `:|:`, not `:|` followed by
  `|:`. Derive it once, from the tree.
- A section label is written as ABC's own inline part marker field, `[P:A]`. A bare
  `[A]` collides with ABC's bracket syntax and corrupts the chord that follows,
  which was verified by conversion through `convertAbcxToAbc`.
- A repeated section is written once, wrapped in `|:` and `:|`. It is not written
  out twice.
- `x` means a held chord and is written as that chord repeated in an ordinary bar.
  It is not a repeat sign.
- Charts are laid out four bars to a line.

New behavior this phase enables, which the current implementation cannot express:

- First and second endings become real ABC ending brackets rather than duplicated
  bars.
- Text annotations are preserved. Determine the correct ABC syntax empirically by
  round-tripping candidates through `convertAbcxToAbc` and checking both that the
  error reporter stays clean and that the chord following the annotation survives
  intact. `[P:A]` was settled this way; do the same here rather than assuming.
- `D.C. al Coda`, `D.S. al coda` and `Fine` can be expressed from
  `IrealChart.navigation` together with the annotation text.

Retire the old path only once the invariants in section 9 hold. Delete
`gridAnnotations.ts`, `gridNotation.ts`, and the superseded helpers in
`importFromIreal.ts` named in section 5.

## 9. Verification harness and invariants

Because this work is permitted to improve output rather than reproduce it byte for
byte, exact output comparison is not available as the oracle, and the invariant set
has to carry that weight instead. Write the harness as a committed script taking
the library path as an argument; do not commit the library itself, which is
personal data.

Suggested location: `parse/ireal/tools/verifyAgainstLibrary.ts`, invoked as
`npx tsx parse/ireal/tools/verifyAgainstLibrary.ts <path-to-backup.html>`.

Invariants, all of which currently hold and none of which may regress:

- Every chart imports with no thrown error and no error reporter entries, except
  entries the harness explicitly expects and lists.
- Zero `UNKNOWN` tokens across the library, or an explicit listed exception set.
- Chord preservation. For each chart, the multiset of chord symbols emitted is
  equal to or a superset of what the current implementation emits. Losing a chord
  fails the run. This replaces byte parity as the primary guard.
- Zero doubled barlines: no `:| |`, no `| |:`, no `:| |:` in emitted ABCx.
- Zero empty bars: no occurrence of `|` followed only by whitespace before the
  next `|`.
- Zero phantom label bars: no `[P:X]` immediately followed by a barline.
- Conversion through `convertAbcxToAbc` reports zero errors for every chart.
- The existing suite stays green: 2596 passing, 14 pending at the time of writing.

The harness should also print a per-chart delta report comparing old and new
output, for human review rather than automatic assertion, since deliberate
improvements will show up there.

## 10. Reference implementations

Consult these for grammar coverage. Follow the precedent set by `scramble.ts`,
which documents that it was reimplemented from a description of the protocol
rather than copied from any implementation's source.

- `drs251/pyRealParser`, MIT licensed, Python. Already cloned during the session
  that produced this plan. Its `_cleanup_chord_string`, `_remove_annotations`,
  `_fill_long_repeats`, `_fill_codas`, `_fill_single_double_repeats` and
  `_fill_slashes` functions between them enumerate most of the constructs in
  section 4, including `r` and `p`.
- `sciurius/perl-Data-iRealPro`, Perl. Independent confirmation of the field layout
  and the obfuscation scheme.
- `ryangavin/yahaha`, which tokenizes bars, sections, repeats and endings.
