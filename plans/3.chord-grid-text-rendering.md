## 1. Why this work exists

Plan 2 built a scanner and a parser for the iReal Pro grid language, and its
section 8 planned a third phase that would emit ABCx from the parsed tree so the
rest of the application could keep working the way it already did. That phase is
superseded by this plan, because the premise underneath it no longer holds.

The premise was that the application needs ABCx. It does not. Of the three views
the application offers, two already bypass ABC entirely and draw a text grid, and
the third draws an engraved staff through abcjs only because a chord chart was
being forced through a notation format that wants notes: the staff holds no
pitches at all, only a run of invisible rests with chord symbols set above them.
Since the engraved staff has been dropped as a requirement, nothing downstream
needs ABCx, ABC, or abcjs.

That matters beyond tidiness. The two text views do not read the parsed tree
today, they read structure back out of the emitted ABCx string by pattern
matching: one pass strips the header lines, a second rewrites chord symbols into
degrees, a third blanks chords for the current cloze level, and a fourth
substitutes glyphs while building HTML. Four string passes, each re-deriving
facts that the tree already states as properties. That is the same mistake plan 2
diagnosed in the import path, displaced one stage later, and it is why the
section letters, the repeat barlines and the held-chord marker each had to be
fixed more than once. Removing ABCx removes the string those passes read, which
removes the class of defect rather than another instance of it.

Two measured consequences come along for free. The emitted ABCx inflates charts
roughly twofold, because it writes a repeated section's text out once per pass
and that duplication compounds: "Caminhando" ships 185 lines with its opening
line recurring verbatim ten times, and "Bole Bole" 634 bars for a tune of 86. A
tree storing each repeat once cannot do that. And first and second
endings, which ABCx expressed by duplicating bars, become a property of the
structure instead.

## 2. What this replaces, file by file

Plan 2 section 8 described `gridToAbcx.ts` and a switchover of
`buildSongAbcxText`. Neither is built. In their place, the parse library gains a
layout step that groups the tree into display lines, and the application gains a
single renderer over that layout.

Retired in `parse/ireal/`:

- `gridAnnotations.ts`, the seventeen successive regex passes that are the
  original cause of the defect class.
- `gridNotation.ts`.
- The superseded helpers in `importFromIreal.ts`: `cellText`, `barlineBetween`,
  `RenderedBar`, `hasMusicalContent`, `compactImmediateRepeats`, and
  `buildSongAbcxText` itself. `irealKeyToAbcKey` is kept but moves, see section 6.

Retired in `chords-mem/src/lib/`:

- `chord-chart-text.ts` entirely. Its `extractChordChartBody` exists only to strip
  ABC headers off a string that will no longer exist.
- `chord-number-chart.ts` entirely, replaced by the renderer in section 6. Its
  glyph table and its superscript treatment are kept, keyed off the parsed
  chord's quality rather than off text.
- `chart-meta.ts` entirely. The key, the tempo, the groove and the style are
  fields of `IrealSongFields`; recovering them from an ABC header we wrote
  ourselves is a round trip through a lossy format for no reason.
- `chord-numbers.ts`'s `applyNotationModeToChordGrid` and `parseAbcKey`. The
  degree arithmetic in `numberNotation.ts` stays and is the whole point; only the
  string rewriting and the ABC key parsing go.
- `chord-cloze.ts`'s `applyChordLevel` and `applyChordLevelToChordGrid`. The level
  definitions and the group arithmetic stay, restated over bars rather than over
  a string.

Also removed: the `abc` and `abcx` fields on a stored chart, the abcjs script tag
and its CDN load check, and `importIrealLinkToAbcx` along with the ABCx splitting
in `ireal-import.ts`.

## 3. The decision that shapes everything else

The parse library must not produce display text, and the application must not
parse any. Every defect this plan exists to prevent came from a stage that
received text and had to recover structure from it, so the boundary between the
two repositories is a structured value, never a string.

Concretely, the library's output is a layout: lines, each holding bars, each bar
holding cells, each cell holding a `ParsedChord`. The application turns that into
HTML or into plain text. The library never decides that a major seventh is
written with a triangle, and the application never decides which bar begins a
line or which barline sits between two bars.

One corollary is worth stating because it is easy to get wrong in the direction
of convenience. The application needs to print a chord's quality, and the
tempting shortcut is for the library to hand over the quality as a string so the
application can pattern match on it for glyph substitution. That reintroduces the
whole problem at the last stage. The application's glyph table is therefore keyed
off `ChordQuality` and the extension number, both of which it receives as values.

## 4. Target architecture

```
irealb:// link
  -> parsePlaylistLink            (fields.ts, exists)
  -> unscramble                   (scramble.ts, exists)
  -> scanGrid                     (gridScanner.ts, phase 1, exists)
  -> parseGrid                    (gridParser.ts, phase 2, exists)
  -> layoutChart                  (gridLayout.ts, phase A of this plan)
  -> renderGridHtml / renderGridText   (chord-grid-render.ts, phase B)
```

Four stages where there were nine, and no stage after the parser consumes a
string.

## 5. Phase A: layout in the parse library

New file `parse/ireal/gridLayout.ts`, with its types in the same file since they
exist only to describe its own output, following the precedent of `gridAst.ts`
holding the parser's types.

```ts
import { ParsedChord } from "../music-theory/types";
import { Annotation, CellKind, IrealChart, Navigation, TimeSignature } from "./gridAst";
```

Types to declare:

```
type Barline = "plain" | "openRepeat" | "closeRepeat" | "closeOpenRepeat" | "final"

interface LaidOutCell
  kind: CellKind
  chord?: ParsedChord
  alternative?: ParsedChord
  bass?: Bass               // an unresolved back reference's bass note
  small: boolean

interface LaidOutBar
  cells: LaidOutCell[]
  openBarline: Barline       // the barline drawn to this bar's left
  annotations: Annotation[]
  fermata: boolean
  endingNumber?: number      // 1 or 2, when this bar belongs to an ending
  indexInChart: number       // 0-based over every bar, for cloze grouping

interface LaidOutLine
  sectionLabel?: string
  timeSignature?: TimeSignature
  sectionIndex: number       // which of IrealChart.sections these bars came from
  bars: LaidOutBar[]
  closeBarline: Barline      // what closes the line; what opens the next is its own

interface ChartLayout
  lines: LaidOutLine[]
  navigation: Navigation
  annotations: Annotation[]  // chart-level, attached to no bar
```

One exported function:

```
layoutChart(chart: IrealChart, options?: LayoutOptions): ChartLayout
```

`LayoutOptions` carries `barsPerLine`, defaulting to 4.

Rules, each of which is a fact the tree already states and which must therefore
be read rather than derived from text:

- A section always starts a new line. Its label and its time signature belong to
  that first line and are not repeated on the section's continuation lines.
- Within a section, bars fill lines `barsPerLine` at a time. A final short line
  is left short and is not padded.
- The barline to a bar's left is a function of that bar and its predecessor, and
  is computed once here. A bar that opens a repeat takes `openRepeat`, one whose
  predecessor closes a repeat takes `closeRepeat`, and the case where both hold
  at once takes `closeOpenRepeat`, which is the single symbol `:|:`. This is the
  rule already settled in `importFromIreal.ts`'s `barlineBetween`; port it, do
  not rediscover it.
- A barline is printed once. Where the two bars it stands between fall on
  different lines, its halves belong at different ends: what closes goes to the
  earlier line's `closeBarline` and what opens to the later line's first
  `openBarline`. Carrying the whole symbol at both ends left a dangling repeat
  sign hanging off the end of a section, on 958 line boundaries library wide.
  The chart's last line closes with `final` instead, since nothing follows it.
- Each line names the section its bars came from. A navigation marker records a
  section index, so a consumer placing one must not have to recover section
  boundaries by counting labels, which would be a consumer re-deriving structure.
- A repeat is laid out once. A `simple` repeat's bars appear once, with
  `openRepeat` on the first and the closing repeat recorded on the bar after the
  last. An `endings` repeat lays out the common bars once, then each ending's bars
  in order, each ending's bars tagged with its `endingNumber`. Only the endings
  before the last send the reader back; the last plays on.
- A section whose bars all live in its endings, which two charts in the sample
  library write, still begins at its first laid-out bar and still heads that line
  with its label. Such a bar does not open a repeat: in the `[N1 ... }` shape the
  repeated span lies before the ending rather than inside it, so an opening
  repeat there would tell the reader to loop one bar.
- Which ending is last is taken from the order the chart writes them in, since
  that is the order it is read in and the numbers are not a reliable ordering:
  the sample library contains a section numbered 2, 1, 2 and another with a lone
  second ending. The harness reports a sequence that is not consecutive from one
  rather than failing, so the shape surfaces instead of passing as ordinary.
- A bar holding no cell is not emitted. The parser already resolves label-only
  bars, so this is a guard rather than a transformation, and the harness asserts
  it never fires.
- `indexInChart` counts bars in layout order, which is the order a reader's eye
  takes, so that cloze grouping matches what is on screen.

Tests in `parse/ireal/gridLayout.spec.ts`, one per rule above, plus one per
defect listed in plan 2 section 1, written in iReal Pro's own chord dialect.
Writing a fixture in ABC's dialect has made correct code look broken three times
in this work: minor is `-7` and never `m7`, major seventh is `^7`, half
diminished is `h7`.

## 6. Phase B: rendering in the application

New file `chords-mem/src/lib/chord-grid-render.ts`. Two exported functions over
one shared traversal, because the HTML view and the clipboard text must never
disagree about what the chart says:

```
renderGridHtml(layout: ChartLayout, opts: RenderOptions): string
renderGridText(layout: ChartLayout, opts: RenderOptions): string

interface RenderOptions
  mode: NotationMode        // 'symbols' | 'nashville' | 'numbers'
  key: KeySignature
  level: ChordLevel
```

How a cell becomes text, in three parts rather than as one string:

- The root. In `symbols` mode it is the chord's root and accidental. In the two
  number modes it is the degree, from `nashvilleDegree` or the mode-relative
  equivalent in `numberNotation.ts`, which now receives the root and the
  accidental as values and no longer parses chord text.
- The quality, from a table keyed off `ChordQuality` and the extension. This is
  where the existing glyph rules live: a major seventh is a bare triangle with no
  seven, a half diminished is a bare circle-slash with no seven, a fully
  diminished seventh is the degree sign, and the accidentals in a degree are the
  unicode flat and sharp. In HTML the quality is set in a `sup`; in clipboard text
  it is plain ASCII in iReal Pro's own convention, since the clipboard is pasted
  into tools that expect that.
- The bass, when present, after a slash, rendered by the same two rules.

This is a deliberate behavior change worth calling out: the chord symbol view
gains the glyphs and the superscript qualities that only the number views had,
because all three views now share one renderer. That is the intent, since the
divergence between them was an artifact of one view going through abcjs.

Cloze hiding becomes a decision per bar rather than a regex over a string. The
level definitions are unchanged and are restated against `indexInChart`: level 1
shows everything, level 2 hides bars whose one-based position within each group
of four is even, level 3 keeps only the first bar of each group, level 4 hides
everything. A hidden cell renders as dashes of the same visible length, which is
what keeps the grid's columns aligned.

Metadata comes from `IrealSongFields`. The key field needs parsing into a
`KeySignature` once, which is the job `parseAbcKey` was doing at the wrong end of
the pipeline: add `parseIrealKey(field: string): KeySignature` to
`parse/ireal/`, beside the existing `irealKeyToAbcKey`, since the iReal key
dialect is the library's business and not the application's. It reads a root, an
optional accidental, and a trailing `-` meaning minor.

`chords-app.ts` loses its branch on notation mode at render time. One path
builds the layout, one renderer draws it, and the mode is an argument.

## 8. What a chart stores

A stored chart keeps the original `irealb://` link and the fields parsed from it,
and nothing derived. The chart is scanned, parsed and laid out when it is
displayed.

The reason is that a parser fix then improves every chart already in the library
rather than only newly imported ones, and there is no performance case against
it: scanning and parsing one chart is well under a millisecond, against a view
that only rerenders on a user action. The alternative, storing a serialised tree,
buys nothing and costs a schema migration every time the tree changes.

Persistent storage itself stays deferred, as decided earlier in this work. This
section fixes what will be stored when it is written, so that the import path
does not have to be rewritten twice.

## 9. Invariants and the verification harness

Extend `parse/ireal/tools/verifyAgainstLibrary.ts`. The library backup is
personal data: the harness takes its path as an argument and the library is never
committed.

The invariant set changes, because the old set guarded properties of an emitted
string and there is no longer a string. What replaces it:

- Every chart in the library scans, parses and lays out with no thrown error and
  no error reporter entries beyond an explicitly listed expected set.
- Chord preservation against the tree, not against the old output. For each
  chart, the multiset of chords in the layout equals the multiset in the tree.
  The layout reorders and groups, and must neither add nor drop.
- Chart length is plausible. No chart's layout exceeds its tree's bar count, which
  is the invariant whose absence let the twofold inflation ship unnoticed. The
  old path's bar count is the baseline being corrected rather than matched, so it
  is deliberately not a target; measured over the sample library the tree holds
  23,532 bars and the layout the same 23,532.
- Every labelled section that lays out a bar contributes exactly one section
  label to the layout, on its first line. A section that lays out no bar at all
  owes no label, since there is nothing for a label to head.
- Barlines, which are the layout's central output and the subject of its whole
  defect history, and so are checked rather than trusted. No repeat sign appears
  at both sides of one line break, no line opens with a barline that closes, no
  `closeOpenRepeat` spans a line break, and the chart's last line ends the chart
  rather than separating it from nothing.
- Chord preservation counts a cell's alternative chord as well as its own, over
  the walk `gridParser.ts` exports for the purpose. A check that forgot the
  alternative branch would pass while every alternative chord in the library was
  being dropped.
- Both renderers agree: for every chart and every notation mode, the chords named
  in the HTML output and in the clipboard text are the same multiset.
- The full suite stays green. It is 4319 passing and 40 pending at the time of
  writing.

## 10. Decisions this plan rests on

Two were put to the user and answered.

- A chart stores the link and is rendered on demand, as in section 8. Nothing
  derived is persisted.
- The ability to emit ABC does not survive, not even as an export. An emitter
  nobody looks at is an emitter whose defects nobody finds, and it can be written
  from the tree later if an export is ever wanted, at which point it is
  `gridToAbcx.ts` from plan 2 section 8 built after phase C and tested as an
  export, with nothing in phases A and B affected.

Two were taken without asking, since the answer is not in doubt, and either can
be overruled. All three views share one renderer, differing only in what a cell
prints. The layout is four bars to a line with a section starting a new line, no
wrapping, and horizontal scrolling on a narrow screen.
